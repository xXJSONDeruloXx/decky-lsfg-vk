# Shaders 26, 27, 28 — 3x3 feature-map convolution family

One spec covers all three shaders. The three SPIR-V modules were diffed after
masking fp16 literal values and canonicalizing SSA ids: they are
instruction-for-instruction identical and differ **only** in the numeric values
of 156 fp16 constants (nine 4x4 tap matrices and three 4-component affine
vectors). Section 6 gives the full per-shader tables; everything else in this
spec is common.

Pipeline role (naming only): each shader reads a 4-channel feature image and
writes a derived 4-channel image.

## 1. Interface

- Entry point: GLCompute `main`, workgroup size **16 x 16 x 1**
  (`OpExecutionMode LocalSize 16 16 1`).
- Capabilities: `Shader`, `Float16`, `ImageQuery`. All convolution arithmetic
  is fp16 (`float16_t` / `f16vec4`); an implementation must do the math in
  16-bit floats to be bit-comparable.
- Descriptors (all descriptor set 0):

| binding | kind | type / format | access | role name |
|---|---|---|---|---|
| 32 | combined image sampler | 2D, float, format Unknown | read (texelFetch only, LOD 0) | `featureTex` (input) |
| 48 | storage image | 2D, `rgba8` (unorm) | write-only (`NonReadable`) | `outTex` (output) |

- No UBO, no push constants, no spec constants.
- Note: binding 32 is declared as a combined image sampler but is only ever
  read with integer-coordinate `texelFetch` at LOD 0; the sampler state is
  never used.

## 2. Indexing conventions

- `gid = ivec2(gl_GlobalInvocationID.xy)`. One invocation produces exactly one
  output texel, stored at pixel `gid`.
- `outSize = imageSize(outTex)`; `inSize = textureSize(featureTex, 0)`.

## 3. Control flow / boundary behavior

1. Early out (the shader guards its own writes):
   `if (gid.x >= outSize.x || gid.y >= outSize.y) return;`
   (ids are unsigned so no negative check is needed.)
2. There is **no** guard of `gid` against `inSize` for the center tap (see
   below). Correct operation relies on the dispatch/wiring guaranteeing
   `outSize <= inSize`; if `outSize` exceeded `inSize`, the center fetch would
   be out of range (undefined under Vulkan without robustness).
3. No loops; the 9 taps are fully unrolled in the fixed order given below.

## 4. Behavior — value stored

Tap offsets, in accumulation order (offset = `(dx, dy)`, added componentwise):

```
o1..o9 = (-1,-1), (-1,0), (-1,+1), (0,-1), (0,0), (0,+1), (+1,-1), (+1,0), (+1,+1)
```

Per-tap input vector (fp32 fetch, then converted to fp16, round-to-nearest-even):

- For every offset **except** `(0,0)`:
  `p = gid + o;`
  `valid = all(greaterThanEqual(p, ivec2(0))) && all(lessThan(p, inSize));`
  `v(o) = valid ? texelFetch(featureTex, p, 0) : vec4(0);`
  (In the original, the `< inSize` half is only evaluated when the `>= 0` half
  passed; the size query has no side effects, so a single combined boolean is
  behaviorally identical. The texture size is queried per tap, at LOD 0.)
- For `(0,0)`: `v = texelFetch(featureTex, gid, 0)` **unconditionally** — no
  bounds check against `inSize` (see section 3).

Accumulation (all fp16):

```
acc = sum over k = 1..9 of  W_k * f16vec4(v(o_k))
```

`W_k * x` is a 4x4 matrix times 4-vector: `out_i = sum_c W_k[i][c] * x[c]`.
The matrices in section 6 are written row-major: row = output channel
(r,g,b,a of the store), column = input channel (r,g,b,a of the fetch).
Terms are added to the running sum in the order o1..o9 above.

Final per-channel affine and store:

```
res  = (acc - A) * B + C          // componentwise, fp16
imageStore(outTex, gid, vec4(res))  // fp16 -> fp32 convert, then rgba8 store
```

The `rgba8` (unorm) store clamps each component to [0,1] and quantizes to 8
bits; this clamping is part of the observable behavior.

*Interpretation (hint, not normative): this is a 3x3 convolution layer with 4
input and 4 output channels and zero padding, followed by a per-channel affine
range mapping so the signed fp16 result fits an 8-bit unorm texture (a
quantization step for a consumer shader).*

## 5. Precision notes

- Fetches return fp32; each is converted to fp16 before use.
- All multiplies/adds (matrix products, accumulation, final affine) are fp16.
- SPIR-V does not pin an evaluation order inside `matrix * vector`; matching
  the listed accumulation order with fp16 `fma`-free arithmetic reproduces the
  original within normal fp16 rounding. Use `f16vec4`/`f16mat4` (or
  equivalent) — doing the math in fp32 will NOT be bit-identical.

## 6. Family parameter tables

Hex fp16 literals are authoritative (exact bit patterns); decimals are for
reading. `W(dx,dy)` is the matrix applied to tap `(dx,dy)`; `A`/`B`/`C` are
the final affine vectors in `res = (acc - A) * B + C` (component order r,g,b,a).
